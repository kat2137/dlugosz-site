## The problem

Sony's configurable controller is designed so that people who cannot use a
standard gamepad can still play. The brief asked what to do with it. Our answer
was to point it outward: most play on a controller is solitary and indoors, and
the same hardware that makes a game reachable can make it social.

The game maps a physical location as an explorable 3D environment seeded with
educational assets: plants, artefacts, buildings. Players move through the real
place and the game responds, with modes for exploring alone and for exploring
together.

## What I built

My part was the controller interaction and the demo. I designed how the game's
functions map onto a configurable controller — which is a harder problem than
mapping to a standard pad, because the input layout is not fixed and the mapping
has to stay legible when the hardware is rearranged. That fed into how functions
signal themselves to the player, which is where the accessibility work actually
lives: if a control can be moved, its meaning has to be communicated by something
other than its position.

If a control can be moved, its meaning cannot be carried by its position. It has
to be carried by something else — so the edge lighting does the work the layout
normally would. Each function has a colour before it has a location.

Six modes came out of that. Break turns every module white to ask the group for a
pause. Emergency flashes red and escalates to a message if it is not cleared.
Torch is triggered by sunset in the detected timezone rather than by a button.
Social flashes the initialisation sequence and then points players toward each
other. Sound gives the D-pad song and volume control. Compass is the default —
green for the right direction, red for the wrong one.

I then built the demo in Unity, animated it fully, and programmed the modes in
C#. It ran on the Sony controller as an interactive demonstration at the SIE
Challenge final presentation.

## What I would change

The demo shows the interactive layer — how commands are issued and how the
controller signals which function sits where. It is not a playable build. The
Unity game runs as a narrative walkthrough, and the controller drives the command
layer beside it rather than the game itself.

Four decisions were specified and then stubbed to get to the presentation, and
they are marked as bypasses on the state machine above: game selection, the
randomised generation of location artefacts, the scoring comparison, and the
translation of another player's coordinates into a direction on the LEDs. The
layer that got built is the one that could be tested in a room with people in it.

With more time the two halves would be one thing — the Unity demo playable end
to end through the controller, so that the configurable layout is tested by
someone actually playing rather than demonstrated alongside a video. That is the
version that answers the question the project is really asking, which is whether
a controller with no fixed layout stays legible under pressure. A walkthrough
cannot answer that.
